# 技术文件助手（JSWJ_DraftbyDSH）

技术文件助手（JSWJ_DraftbyDSH），以下简称本插件。两条业务流共用一个知识空间：业务流 1 创建技术文档（7 步），业务流 2 技术资料 AI 预审（5 步）。
每一步先满足门禁再进入下一步，不得跳步。出稿一律走「渲染 Word → 发布知识库」，不得用纯文本冒充正式文件。

## 核心原则：模板是底座

- 本插件所有业务 Word（预览稿、正式稿、修订稿）必须从 GY-F003 模板渲染，禁止直接手搓 docx、换模板或另起一套排版。
- 预览、出稿、修订共用同一个 `jswj_render_docx` 渲染器；不允许某条路径绕过模板。
- 模板规则集中维护在 `python/render_docx.py`，包括：封面、页眉页脚、分节页码、章节编号、列表编号、题注、图/表目录、表格列宽、合并单元格、多行表头、会签表。
- 「套用模板」是本插件的基础底层能力，不是可选的收尾步骤；修改模板相关代码后必须按「出稿前检查清单」逐项回归。
- 模板文件 `template/GY-F003-cleaned.docx` 是唯一版式来源；不要在业务代码里硬编码字体、页边距或页码。

## 前置检查

1. 先调用 `jswj_ping`。返回 `ok: true` 才继续。
2. 返回里要核对四件事：空间名是否为「技术资料起草库」、`rootNodes` 是否包含目标父节点、
   `python` 是否可用、`template.exists` 是否为 true。
3. 缺少 `appId` / `appSecret` / `spaceId` 时，直接指出缺哪一项并停止；不要改用其他方式访问知识库。
4. 工具未注册时，说明 `jswj-draft` bundle 未安装或未生效，停止流程，不要绕行。

可用工具：

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `jswj_ping` | 配置自检 | 无 |
| `jswj_wiki_list` | 列出节点下的子节点 | `parent?`（省略用 rootToken） |
| `jswj_doc_read` | 读取在线文档纯文本 | `target`：wiki/docx 链接或 token |
| `jswj_wiki_create` | 新建 docx 节点 | `parent?`、`title` |
| `jswj_doc_append` | 向文档追加纯文本段落 | `target`、`content` |
| `jswj_render_docx` | Markdown → GY-F003 Word | `title`、`markdown` 或 `sourcePath`、`baseDir?`、`classification?` |
| `jswj_publish_docx` | .docx 上传并移入知识库 | `filePath`、`parent?`、`name?` |
| `jswj_task_get` | 读取页面任务状态 | `taskId` |
| `jswj_task_update` | 把生成/自检/预审/修订结果写回任务 | `taskId`、`patch`（JSON 字符串） |

## 页面任务（分步向导）

页面发起的任务以 `【JSWJ 任务 DOC-xxxx · 第 N 步：xxx】` 开头。处理顺序：

1. 调 `jswj_task_get` 读取任务，确认 `flow`、`step` 与已有 `data`；
2. 只执行当前 `step` 要求的工作，不越过当前步去做后面的步骤；
3. 完成后调 `jswj_task_update` 写回结果，用户回页面点「刷新」继续。

写回形状（patch 是 JSON 对象字符串）：

| 步骤 | 写回 |
|---|---|
| ⑤ 生成 | `{"data":{"generation":{"status":"done","note":"..."},"draft":{"markdown":"# 标题\n...","ready":true,"version":1,"confirmed":false}}}`；自检与修订在同一回合内完成 |
| ⑥ 成稿确认 | 按 `draft.comments` 定向修订后写回 `draft.markdown`、`draft.version` 加 1、`draft.ready` true、`draft.confirmed` false |
| ④ 预审 | `{"data":{"review":{"issues":[{category:"内容完整性|定量与数据|插图与标注|编号与引用|一致性与追踪|格式与规范|附录与附件",severity:"严重"或"建议",location,problem,basis,suggestion,evidence:{quote,section,figure,annotations}}],"checkedFigures":[{"file":"img-01.png","caption":"图 8-1 ...","result":"已查看、无疑点"}],"summary":"文字类 N 条、图类 M 条、切片数 K、查图数 J","failedSlices":[]}}}` |


**评审意见必须带证据（evidence）**，用于在页面上回显原文与位置：

- `quote`：受审文件里连续 20–40 字原文，逐字复制，不改写、不拼接两处
- `section`：章节号，如 `6.1`、`7.3`
- `figure`：图类意见的 figure 可填 `figures.json` 中对应条目的 `file`（如 `img-01.png`）；也可填图号（如 `图 6-1`）或题注，页面会按题注匹配。非图类留空
- 图类意见（分辨率、复用、图例缺失）以 figure 定位，quote 填图题注
- 图片类意见必须给 `annotations`，定位到图中具体区域，不要整图圈选。坐标按相对比例估算（0–1，相对图片左上角），支持四种形态：`rect`（实线红框）、`ellipse`（红圈）、`arrow`（箭头指向）、`spotlight`（压暗四周、只留亮区），每项写成 `{shape, x, y, w, h, label?}`。示例：图上某个表头错字 → 框住该单元格 `{shape:"rect",x:0.42,y:0.18,w:0.12,h:0.05}`。
- 同一张图有多个问题时给多条 `annotations`，`label` 依次编号（1–2 个字符）。只有确实无法判断精确位置时才省略，页面会退化为整图 1px 虚线红框。
- quote 必须能在任务 sources[].textPath 或受审文件解析出的 text.txt 里原样搜到；搜不到说明摘错了，须重摘

任务文件在 `~/.dsh/jswj-tasks/<任务号>.json`，不要手工改；只通过工具读写。

同一步优先复用任务 `sessions` 里记录的会话；修订与生成都以任务里的 `draft.markdown` 为准，不依赖聊天历史，换会话不会丢正文。

页面 D3 上传的 docx / md 会留存到知识库 `参考资料库/{层级}/{板块}/`，任务 `sources[]` 里带 `textPath`（本地纯文本）；需要读资料内容时直接读该文件，不要尝试用 `jswj_doc_read` 读 file 类型节点。

参考资料参考程度看 `sources[].mode`：

- `mirror` 原样套模板：跳过实际起草，章节结构、正文内容、表格与图片全部按参考资料原样保留，不做内容改写，只按 GY-F003 排版。
- `template` 参考写法：沿用章节结构、行文语气、表格与内嵌图片，按本次主题重写内容。
- `mirror` 与 `template` 不合并：前者内容是“照搬”，后者内容是“按新主题重写”，能力不同；界面上用“原样套模板”和“参考写法”区分。
- `structure` 参考章节结构：沿用章节层级和顺序，正文重写，不照搬行文。
- `background` 背景资料：只取事实、数据与约束，重新起草，不照搬结构。

多份参考资料时：

- 每份资料单独选参考程度，可混用不同模式。
- 「原样套模板」最多只能选一份，作为整篇底稿；其他资料只能补充、校验或提供章节结构，不能同时作为第二份照搬底稿。
- 建议指定一份主参考：`mirror` 或 `template` 为主，其余用 `structure` / `background`。资料越多、模式越杂，助手需要权衡的约束越多，正文质量和速度都会下降；优先控制在 3～5 份以内。

上传 docx 的内嵌图片已抽到 `sources[].images`（本地绝对路径）；`mirror` / `template` 模式可直接在 Markdown 中引用这些图片，`structure` / `background` 模式不要直接套用图片。

生成：逐章生成正文后，在同一回合内自动自检并修订到没有严重项，再把 `generation.status=done`、成稿正文 `draft.markdown`、`draft.ready=true`、`draft.version` 写回任务。不要让用户逐步确认自检与修订。

成稿确认：用户把意见写在 `draft.comments`。按意见逐条定向修改，只改意见指出的位置，不整体润色、不补写整节；完成后 `draft.version` 加 1、`draft.ready=true`、`draft.confirmed=false`，并写回任务。

## 知识库落位

当前知识空间根级只有三份 docx：

```
技术资料起草库（space 7698962670346636559）
├── 首页
├── 技术文件模板          ← 模板说明，不作正文落位
└── 技术资料草稿库        ← 出稿默认父节点（jswj_ping 的 draftRootToken）
```

落位规则：

- 出稿默认父节点用 `draftRootToken`；预审意见书可放在任务目录下。
- 业务目录由文档属性推导，不要让用户手工填路径：
  `{层级}/{板块}/{文件类型}/`，层级 `T0 飞机级`、`T1 系统级`、`T2 子系统级`、`T3 设备级`、`T4 软硬件级`、`T5 零件级`；
  板块如 `总体`、`电子`、`试验试飞`、`动力`；文件类型如 `需求规范`、`技术方案`。
- 写入前用 `jswj_wiki_list` 确认父节点存在且名字匹配；缺失时用 `jswj_wiki_create` 逐级创建，并复述创建结果。
- 目录不确定时先列出来问一次，不要猜一个相近的目录就写。

## 业务流 1 · 创建技术文档

| 步 | 动作 | 门禁 |
|---|---|---|
| ① 基本信息 | 收集文件名称、文件类型、密级（L1/L2/L3）、编号（可空） | 名称非空；类型与密级已选 |
| ② 文档属性 | 收集层级、板块、归档位置，推导目标目录 | 三项齐备；目录可创建 |
| ③ 参考资料 | 接收飞书云文档链接或上传件，逐份复述解析结果 | 至少一份解析成功；失败项剔除 |
| ④ 大纲与纲要 | 依据资料与模板出完整大纲（到三、四级）；只就一、二级确认要点 | 覆盖模板必备章节；要点齐备或标注「由 AI 拟稿」 |
| ⑤ 生成 | 逐章生成正文；表格结构化；图形有数据才画 | 全部章节完成 |
| ⑥ 成稿确认 | 看成稿、提意见；助手按意见定向修订 | 成稿已生成且确认 |
| ⑦ 出稿 | `jswj_render_docx` 出 Word → `jswj_publish_docx` 发布到目标目录 | 文件已落位，节点回执与链接已给出 |

补充约束：

- 编号留空时文件名只用文档名称，不生成临时编号。
- 封面签署栏与会签表留空，由标准化部门在审批环节填写。
- 修订只改意见指出的位置，不整体润色，不补写整节。

## 业务流 2 · 技术资料 AI 预审

| 步 | 动作 | 门禁 |
|---|---|---|
| ① 确认 | 说明范围与预计耗时，取得用户确认 | 已确认 |
| ② 类型与评审单 | 确认评审类型（需求规范 / 技术方案 / 安全性文件 / 审定计划），加载评审单并复述编号与版本 | 类型与评审单适用类型一致 |
| ③ 文件与资料 | 接收受审文件（必需）与参考资料（可选） | 受审文件解析成功 |
| ④ 预审 | 第 1 遍文字审查（按阈值切片并行）→ 第 2 遍图审查（故障树按阈值分组并行）→ 总合并去重、排序、写回 | 两遍完成；故障树逐张留痕；`review.summary` 已写回 |
| ⑤ 意见与修订 | 输出意见清单并存档；询问是否协助修订 | 意见书已写入任务目录 |

### 评审单：审定计划（v1，39 项）

适用对象：型号合格审定计划、系统/专业审定计划、专项合格审定计划（PSCP/CP），以及作为审定计划附件的符合性验证思路、符合性检查单、符合性文件清单。

审查原则：

- 审的是“计划是否可作为后续符合性工作的依据”，不替代产品符合性检查。
- 正文、附件 1（验证思路）、附件 2（符合性检查单）、附件 3（文件清单）四处的条款、MC、文件、试验必须交叉核对；任一处不一致按“严重”记录。
- 审定计划的结论只能是“具备提交审查条件 / 需补充后提交”，不输出产品“通过/不通过”。
- 每条意见必须引用章节号、表号或附件号；无法定位时标注「缺依据」。

检查项：

1. 文件编号、版本、密级、编制/校对/审核/批准、会签是否完整。
2. 修订记录与正文版本、日期是否一致。
3. 引用文件清单是否齐全，编号、版次、日期是否有效。
4. 是否存在 `XXXX`、`TBD` 等占位符，是否已列入开放项。
5. 术语、缩略语、系统名称在全文是否统一。
6. 目录、页码、章节号、表号、图号、附件编号是否对应。
7. 系统的物理边界、逻辑边界和对外接口是否清楚。
8. 与关联审定计划的分工、接口、引用关系是否明确。
9. 排除项、不适用项及其边界是否有依据。
10. 运行场景、使用限制、环境包线是否与审定基础、安全性假设一致。
11. 系统功能清单是否完整，功能编号是否唯一、可追溯。
12. 系统组成、架构、余度、资源分配的描述是否前后一致。
13. 安装位置、供电、对外接口、维护接口是否明确。
14. 构型项、PN、软硬件版本、供应商交付边界是否明确。
15. 审定基础条款清单是否完整。
16. 每条条款的适用性判定是否明确。
17. 不适用条款的理由是否充分、可接受。
18. 专用条件、豁免、等效安全是否纳入并说明。
19. 条款是否分解到系统、设备、软件、硬件层级。
20. 失效状态分类是否与 SFHA/PSSA/SSA 一致。
21. FDAL 分配是否有方法、有依据。
22. IDAL 分配是否与 FDAL、软件/复杂电子硬件类别一致。
23. 定量概率指标、失效状态类别是否与运行场景匹配。
24. 单点失效、共因失效、冗余独立性是否分析。
25. 安全性结论是否与关联安全性审定计划一致。
26. 每个适用条款是否至少有一种符合性方法（MC），选择理由是否充分。
27. MC 是否与条款、符合性文件、责任人、CVE 对应。
28. 条款—MC 矩阵在正文、附件 1、附件 2 三处是否一致。
29. 试验矩阵是否覆盖条款、功能、接口和安全性验证。
30. 试验件、试验环境、通过准则、数据采集是否明确。
31. 首飞前、TIA 前、取证前节点及依赖关系是否明确。
32. 试验供应商、地点、资源、风险是否可控。
33. CDI 划分是否与 CPI/审定计划项一致。
34. LOI 是否有风险分析依据，CVE 是否明确。
35. 制造符合性检查项目、检查依据、TIR 是否对应。
36. 条款→MC→文件→试验→CDI→LOI 是否形成闭环、可追溯。
37. TBD/开放项是否有责任人、关闭时间、影响分析。
38. 变更控制、版本更新、与关联 CP 的同步机制是否明确。
39. 审查结论、遗留问题、签署栏是否完整。

输出要求：

- 每条不符合项写：检查项编号、位置、问题、依据、建议改法、严重程度。
- 同一问题在正文和附件重复出现时合并为一条，注明涉及的全部位置。
- 仅涉及格式、编号、文字统一的问题记“建议”；影响条款适用性、MC 选择、验证闭环、安全性结论的问题记“严重”。

补充约束：

- 意见只有两档：**严重**（不符合评审单要求或缺依据）、**建议**（可改进）。不作门禁。
- 每条意见须含位置、问题、依据、建议改法；无法定位的不写，宁可标注「缺依据」。
- 参考资料缺失时，依赖依据的检查项一律标注「缺依据」，不得默认符合。
- 协助修订限于意见指出的位置；原件保留，修订版另存，两者与意见书同目录。
- 不输出「通过」或「不通过」的结论。是否通过由人判断。

## 预审执行协议（两遍 + 总合并）

预审第 ④ 步按以下顺序串行执行，前一阶段完成后再进入下一阶段：

1. 第 1 遍：文字审查
2. 第 2 遍：图审查
3. 总合并：两遍结果去重、排序、写回任务

两遍各自独立产出意见。第 1 遍不打开 `images/`，不讨论图；第 2 遍不重复提文字类问题。

### 一、切片阈值

- 正文纯文本超过 **80,000 字**才切片；不超过 80,000 字整篇一次审。
- 文字片数 = `min(8, ceil(字数 / 30000))`。示例：95,000 字 → `ceil(95000/30000)=4` 片。
- 故障树类图超过 **12 张**才分组；不超过 12 张逐张串行。
- 图组数 = `min(6, ceil(故障树图数 / 12))`；按图号顺序切，每组不超过 12 张，除最后一组外不少于 8 张。示例：13 张 → 2 组（8 + 5）。
- 同时执行的子任务上限为 **6**。

切片规则：

- 按一级或二级标题边界切，不从句子中间断开。
- 每片开头附共享背景：文件标题、章节目录、术语与缩略语、关键表格编号与标题（如表 6.1、7.x 的标题列表）。
- 每片标注自己的章节范围，如「第 5.1–5.4 节」，供合并时归位。
- 切片写入任务目录 `slices/`：`s01.txt`、`s02.txt`……，并写 `slices/manifest.json` 记录每片的 `file`、`range`、`chars`。

### 二、第 1 遍：文字审查

范围：正文段落、表格、章节编号与交叉引用、结论与数据一致性。只依据 `textPath` 抽出的正文与表格，不打开图片，不讨论图。

检查项（6 项）：

1. 内容完整性：评审单要求的章节、条目是否齐备。
2. 定量数据与来源：数值是否有出处、单位与口径是否一致。
3. 表格与正文一致：表内数据、表题、正文引用是否一致。
4. 编号与命名：章节、图表、缩略语编号是否唯一、连续、可追溯。
5. 引用与附录对应：正文引用的表、图、附件是否真实存在并能对应。
6. 结论是否有支撑：结论是否能由正文数据与依据推出。

输出要求：

- 每条意见的 `evidence` 只写 `quote`（原文连续 20–40 字）与 `section`。
- `evidence` 不带 `figure`，不带 `annotations`。
- 每条意见必须给出图号、表号或章节号作为依据；拿不到依据时写「缺依据」。

### 三、第 2 遍：图审查

范围：`images/` 下的插图，重点是故障树。

流程（3 步）：

1. 读 `~/.dsh/jswj-sources/<任务号>/figures.json`，按题注分类：故障树类（题注含「故障树」「FT」「FTA」）、架构类、其他。`figures.json` 缺失时，按 `images/` 文件名与正文题注建立临时映射，并在 `review.summary` 注明「缺 figures.json」。
2. 故障树逐张打开 `images/<file>` 实际查看；架构类在题注涉及接口、安装或架构且需要核对图文关系时打开；其他图仅在已有意见指向该图时打开。
3. 每张打开过的图记一条处理痕迹：有问题的写入 `review.issues`；无问题的写入 `review.checkedFigures`，格式为 `{"file":"img-33.png","caption":"图 8-31 ...","result":"已查看、无疑点"}`。筛出的故障树图不得遗漏。

附录筛选：

- 在正文中找标题含「附件」「附录」的章节及其章号。
- 在 `figures.json` 中筛出该章号范围内、题注含「故障树」「FT」「FTA」的图。
- 图号范围无法判断时，筛出所有题注含上述关键词的图并逐张查看。

故障树检查维度（6 项）：

1. 结构完整性：顶事件是否与报告声明一致；每个中间事件是否都有下层展开；有无悬空或无下层的分支。
2. 门类型：与门/或门标注是否与文字描述相符；文字写「同时发生」而门标注为或门，按疑点记录。
3. 定量：底事件概率是否与表 6.1、7.x 等正文表格一致；按门结构合成的顶事件概率是否与报告声明值吻合。
4. 割集：正文给出的最小割集数量、阶数是否与树结构自洽；共享底事件是否被当作独立事件重复计算。
5. 依赖：共因失效是否识别（同一供电、同一总线、同一软件、同一传感器组合）；标称冗余是否真独立。
6. 一致性：不同图之间是否复制粘贴后改名；同一失效状态在不同图的编号、命名是否一致。

每条结论必须给出概率数值、图号、表格编号中的至少一项作为依据；没有依据时写「缺依据」。

定量核算：

- 每棵主要故障树至少做一次合成计算。
- 与门：`P = ∏ pi`。
- 或门：`P = 1 − ∏ (1 − pi)`。
- 底事件概率缺失时标 `TBD`，不得默认取值。
- 计算结果与报告声明值比较；偏差超过一个数量级或门结构明显不符时，判「严重」，并把门结构、各底事件概率、公式与计算结果写进 `problem` 字段。

输出要求：

- 图类意见的 `evidence` 必须带 `figure`（真实文件名，如 `img-33.png`）与 `annotations`（框出问题门或分支，`shape` 用 `rect` 或 `ellipse`）。
- `quote` 填该图题注或图中可读的事件名。
- 意见摘要写清：哪棵树、哪个门、哪些底事件。

### 四、并行派发规范

用 DSH 的 `workflow` 工具或 `subagent` 派发切片任务；一次预审中的并发不超过 6。

- 文字切片：每片一个子任务。提示词必须内含本遍的 6 项检查清单、共享背景、章节范围、输出 JSON schema；子任务不依赖读取本技能文档。
- 图分组：每组一个子任务。提示词必须内含该组图的 `file`、`caption`、6 个故障树检查维度、定量核算公式、annotations 输出要求；子任务不依赖读取本技能文档。
- 输出统一为 JSON 数组，每条含 `category`、`severity`、`location`、`problem`、`basis`、`suggestion`、`evidence`；`severity` 仅「严重」「建议」。
- `category` 只能取七类之一：`内容完整性`、`定量与数据`、`插图与标注`、`编号与引用`、`一致性与追踪`、`格式与规范`、`附录与附件`；图类意见归 `插图与标注`。
- 子任务之间不互相等待；主任务在所有子任务返回后统一合并。并发上限 6，超过时排队。
- 子任务不负责写任务文件；只返回 JSON，由主任务写回。

### 五、总合并

1. 合并：把两遍、所有切片的意见合并成一个 `review.issues` 数组。
2. 去重：按 `evidence.quote` 归一化（去空白与标点）后相同，且位置与问题实质相同，视为同一条；保留描述更具体的一条。不同位置出现的同类问题各自保留；不把相似问题合并成「同类问题计 N 处」，除非用户明确要求汇总。
3. 意见数量不设上限。不为条数好看而合并、删除或降级任何独立问题；合并后某章节超过 20 条时按章节分组呈现，不精简。
4. 严重程度按实质判定，不因某类意见条数多而下调。
5. 排序：按章节号升序；图类意见按 `evidence.section` 或图号所属章节归位；编号按排序后的数组顺序连续重排。
6. 跨章复核：合并后主任务再通读 `textPath`，专门核对跨章矛盾（如 5.5 与 6.3 对同一事实表述相反），这类问题单片审不出来，复核结果并入 `review.issues`。
7. 统计：在 `review.summary` 写一行：`文字类 N 条、图类 M 条、切片数 K、查图数 J`；有失败片时追加 `、失败片 X 个`。
8. 写回：`review.issues`、`review.checkedFigures`、`review.summary`、`review.failedSlices` 一次写回任务。

### 六、失败处理

- 某片超时或返回非法 JSON：重试一次。
- 重试仍失败：写入 `review.failedSlices`，每项含 `file`、`range`、`error`；在意见书中注明「第 X 片未完成」，不得用空结果冒充。
- 任一片失败不影响其他片的结果写回；`review.summary` 标注失败片数量。

### 七、故障树定量核算示例

示例（用于说明计算与写回格式）：

- 图号：图 8-31「丧失全部三轴加速度信息定量故障树」，`figure = "img-33.png"`。
- 门结构：`T = E1 OR E3`；`E1 = E2 AND E4`。
- 底事件（表 7.40）：`P(E2)=1.2E-5/FH`、`P(E4)=3.4E-6/FH`、`P(E3)=2.0E-7/FH`。
- 计算：
  - `P(E1)=1.2E-5 × 3.4E-6 = 4.08E-11`
  - `P(T)=1 − (1 − 4.08E-11) × (1 − 2.0E-7) = 2.00004E-7 ≈ 2.0E-7/FH`
- 报告表 6.1 声明 `5.0E-9/FH`；偏差 `2.0E-7 / 5.0E-9 = 40` 倍，超过一个数量级，判「严重」。
- 写回：`location = "8.31"`；`problem` 写入上述门结构、概率来源、公式、结果与偏差；`basis = "表 6.1、表 7.40、图 8-31"`；`evidence.figure = "img-33.png"`；`evidence.quote = "图 8-31 丧失全部三轴加速度信息定量故障树"`；`evidence.annotations = [{"shape":"ellipse","x":0.42,"y":0.12,"w":0.12,"h":0.08,"label":"1"},{"shape":"rect","x":0.18,"y":0.34,"w":0.22,"h":0.10,"label":"2"}]`。
- 底事件概率为 `TBD` 时，`problem` 写明「P(T) 不可复算：E2、E4 为 TBD」，不得代入默认值，也不得给出合成结果。

## Word 出稿规范

Markdown 结构决定 Word 结构：

- 一级标题 `#` 视为文档标题，只用于封面，不进入正文。
- `##` → 1 级标题，`###` → 2 级，`####` → 3 级；更深层级按 3 级处理。
- 表格用标准 Markdown 表格；分隔行之前都是表头，之后首列为空、其他列有短标题的续行也按多行表头处理。
- 表格前一行必须写题注：`表 {章}-{序号} 标题`；附录单号表写 `表 22 标题`。
- 图片用 `@@IMG 相对路径 宽度cm@@`，相对路径以 `baseDir` 为准；优先传绝对路径。
- 图片后一行必须写题注：`图 {章}-{序号} 标题`。
- 题注由渲染器转成 Word 的 Caption + SEQ 域，图目录、表目录据此自动生成；没有题注的图/表不会进入目录。
- 长文档先写入本地 `.md` 文件，再用 `sourcePath` 渲染，避免把整篇正文塞进工具参数。

`jswj_render_docx` 必填 `title` 与 `markdown`/`sourcePath` 之一；`docNumber` 传任务的 `basic.number`，会同时写入封面和页眉右上角。密级默认 `L2 重要/秘密`，编制默认空，校对与审核默认「待定」。生成后复述本地路径与大小。

发布：

- `jswj_publish_docx` 的 `filePath` 必须是 `jswj_render_docx` 返回的绝对路径。
- `parent` 省略时落到 `draftRootToken`；发布到任务目录时显式传该目录节点 token。
- `name` 用「{编号?}-{文件名称}-{版本}.docx」，编号为空则不带前缀。
- 发布成功后必须给出 `wikiToken` 与 `url`，并把它记为本次出稿回执。
- 发布失败时保留本地产物与返回的 `file_token`，不要重新渲染后再上传一遍。

## 排版经验（已踩过的坑，必须遵守）

### 章节编号

- 章节号以源 Markdown 标题里的编号为准，如 `## 2 引用文件和标准规范`、`### 2.1 ...`。
- 必须取消 Word 标题样式的自动多级编号，否则二级标题会跨章连续成 1.5、1.6、1.7。
- 题注的章号从当前一级标题编号读取，不要用 `STYLEREF 1 \s` 去猜，模板标题编号不一定生效。

### 列表

- 有序列表按模板编号：第一级 `a)`、`b)`，第二级 `1)`、`2)`；每个列表块重新编号，不能沿用 Markdown 里跨小节的 4、5、6、7。
- 条目之间即使有空行，只要后面仍是编号条目，就属于同一个列表块，应连续编号。
- 每个新标题下的列表重新从 1 开始。
- 无序列表左缩进约 0.35 cm，首行缩进必须显式写 `firstLineChars=0`，不能继承正文的 2 字符首行缩进，否则项目符号会显得缩进过大。

### 图目录与表目录

- 复用模板原有的「图目录」「表目录」TOC 域，不要自己再插一套目录，否则会出现两套。
- 题注用 Word 的 Caption 样式 + `SEQ 图/表` 域；图目录、表目录用模板的 `TOC \c "图"` / `TOC \c "表"` 域更新。
- 题注编号带章号时用「章-序号」；附录里的单号表（如 `表 22`）沿用源编号，不强行套章号。
- 预览稿和正式出稿走同一套渲染逻辑，目录页码都要在生成时更新好。

### 表格

- 列宽按整列内容篇幅和最长单元格共同分配；长段落多的列必须拿到更宽，不能只看表头或最长一行。
- 中文按 2 个字符宽度计算，列宽下限约 1.9 cm；表头列可适当加宽。
- 多列都很宽、总宽超版面时，按内容权重压缩，不能等比压成等宽，否则长文本列会被挤成细条。
- 分组列（序号、系统功能、研制阶段、阶段、过程、类型、类别）中，相邻相同值或空续行要纵向合并单元格，不要每行重复。
- 阶段对照表这类跨行语义列（如“高域GAC-A6飞机的研制阶段”）也要按相同值纵向合并，不能只限固定表头。
- 单元格统一单倍行距、段前段后 0，避免多行文字叠在一起。
- 表头按一行设计；需要多行时（如“集成与验证阶段”下再分“集成/验证/试飞测试/适航验证/总结”）横向、纵向合并，不能当成正文行。
- 多行表头必须整块保持在同一页，所有表头段落设置 keep_with_next，避免“试飞测试/适航验证”被分页甩到下一页。
- 横向合并的表头单元格宽度必须等于所跨列宽之和，否则“验证”的右边框会和“适航验证”对不齐。
- 多行表头横向合并只能延伸到同一父表头列内，不能把“总结”并进“适航验证”；“集成/总结”要纵向跨两行。
- 表格题注放在表格前一行，图片题注放在图片后一行。

### 封面与页眉

- 封面两条横线是模板里的图形对象，清理模板时不能当批注删掉。
- 文件编号同时写入封面表格和页眉右上角，格式为 `文件编号：{编号}`。
- 编制、校对、审核、批准、版本取任务 `basic` 的对应字段；没有值时保留「待定」，不要留模板里的 `XXXX`。
- 变更记录表按 `basic.revisions` 渲染，每行一个版本；至少保留「A0 新发文件」，后续修订逐行追加版本、说明、责任人、日期。
- 首次出稿默认 `A0 新发文件`，不要自行升 A1 或加修订行；只有用户明确要求改版时才升版本。
- 会签栏和签名页是**单份文件内容**，不要写进模板；按任务 `basic.signers` 渲染，模板保持空白占位。
- 会签表增行时必须复制模板原有数据行，保留行高、字体、边框和单元格对齐，不要用默认新行重建。
- `jswj_render_docx` 的 `docNumber`、`author`、`checker`、`reviewer`、`approver`、`version` 要与任务 `basic` 一致。

### 页码

- 保留模板原有的分节：封面、修订页不显示页码；图目录/表目录用罗马数字；正文用阿拉伯数字并从 1 重新开始。
- 正文页脚保留模板的 PAGE / SECTIONPAGES 域，显示“第 X 页 共 Y 页”。
- 不能把文档收敛成单节，否则会丢失目录罗马页码和正文重新编号。

### 自动预览

- 生成完成后自动出预览稿。
- 自动预览是异步的；如果用户已经点「确认成稿」推进到下一步，旧的预览响应不得把页面状态覆盖回上一步。

### DSH 升级兼容

- DSH 升级后会校验插件的 `inject`；使用 `ctx.webServer` 必须把 `webServer` 写进 `inject`，否则页面所有 `/api/jswj` 请求都会 404，但工具本身仍然可用。
- 出现“HTTP 404 / 插件自检发现 1 项问题”时，先看插件激活诊断，再看路由是否注册，不要先怀疑飞书凭据。

### 出稿前检查清单

每次生成预览稿或正式出稿后，必须打开实际 docx 逐项核对，不能只看任务状态：

| 检查项 | 要求 |
|---|---|
| 封面信息 | 密级、名称、编制、校对、审核、批准、版本、文件编号齐全，无 `XXXX`、`A0/A1/A2` |
| 页眉 | 右上角为 `文件编号：{编号}` |
| 封面线 | 标题下、公司名上两条横线都在 |
| 图/表目录 | 只有模板原有的一套，条目和页码正确，无“未找到图形项目表” |
| 页码 | 封面/修订页无页码；目录罗马数字；正文阿拉伯数字从 1 开始，页脚“第 X 页 共 Y 页” |
| 章节编号 | 分章重新开始，如 1、1.1、2、2.1，不出现跨章连续 1.5/1.6 |
| 列表 | 第一级 `a)`、`b)`，第二级 `1)`、`2)`；每个列表块重新编号；无序列表左缩进约 0.35 cm，首行不额外缩进 |
| 表头 | 表头不被拆成“时间进度安 / 排”，多行表头层级正确 |
| 列宽 | 长文本列拿到足够宽度，不被压成细条 |
| 合并单元格 | 序号、系统功能、研制阶段、过程等分组列及阶段对照表按相同值纵向合并 |
| 多行表头 | 集成/验证/试飞测试/适航验证/总结层级正确，整块同页，验证右边框与适航验证对齐 |
| 变更记录 | 首次出稿只有 `A0 新发文件` 一行，不擅自升 A1 |
| 会签栏 | 只写本文件，不写入模板；人员和部门按任务数据 |

## 用户意见与版本规则

- 每次成稿意见记录在任务 `draft.commentHistory`，任务完成时随总结写入多维表格的「用户意见」列。
- 单条意见只作用于当前任务，不直接改全局规则。
- 版本发布时，把高频、可复用的意见归纳进本技能与页面提示，随插件一起分发给所有用户；未经归纳的意见不进入全局。

| 情况 | 处理 |
