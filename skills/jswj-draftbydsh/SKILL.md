# 技术文件起草（JSWJ_DraftbyDSH）

技术文件起草（JSWJ_DraftbyDSH），以下简称本插件。两条业务流共用一个知识空间：业务流 1 创建技术文档（7 步），业务流 2 技术资料 AI 预审（5 步）。
每一步先满足门禁再进入下一步，不得跳步。出稿一律走「渲染 Word → 发布知识库」，不得用纯文本冒充正式文件。

## 前置检查

1. 先调用 `jswj_ping`。返回 `ok: true` 才继续。
2. 返回里要核对四件事：空间名是否为「技术资料起草库」、`rootNodes` 是否包含目标父节点、
   `python` 是否可用、`template.exists` 是否为 true。
3. 缺少 `appId` / `appSecret` / `spaceId` 时，直接指出缺哪一项并停止；不要改用其他方式访问知识库。
4. 工具未注册时，说明 `jswj-draft` bundle 未安装或未生效，停止流程，不要绕行。

可用工具：

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `jswj_ping` | 配置自检 | 无 |
| `jswj_wiki_list` | 列出节点下的子节点 | `parent?`（省略用 rootToken） |
| `jswj_doc_read` | 读取在线文档纯文本 | `target`：wiki/docx 链接或 token |
| `jswj_wiki_create` | 新建 docx 节点 | `parent?`、`title` |
| `jswj_doc_append` | 向文档追加纯文本段落 | `target`、`content` |
| `jswj_render_docx` | Markdown → GY-F003 Word | `title`、`markdown` 或 `sourcePath`、`baseDir?`、`classification?` |
| `jswj_publish_docx` | .docx 上传并移入知识库 | `filePath`、`parent?`、`name?` |
| `jswj_task_get` | 读取页面任务状态 | `taskId` |
| `jswj_task_update` | 把生成/自检/预审/修订结果写回任务 | `taskId`、`patch`（JSON 字符串） |

## 页面任务（分步向导）

页面发起的任务以 `【JSWJ 任务 DOC-xxxx · 第 N 步：xxx】` 开头。处理顺序：

1. 调 `jswj_task_get` 读取任务，确认 `flow`、`step` 与已有 `data`；
2. 只执行当前 `step` 要求的工作，不越过当前步去做后面的步骤；
3. 完成后调 `jswj_task_update` 写回结果，用户回页面点「刷新」继续。

写回形状（patch 是 JSON 对象字符串）：

| 步骤 | 写回 |
|---|---|
| ⑤ 生成 | `{"data":{"generation":{"status":"done","note":"..."},"draft":{"markdown":"# 标题\n...","ready":true,"version":1,"confirmed":false}}}`；自检与修订在同一回合内完成 |
| ⑥ 成稿确认 | 按 `draft.comments` 定向修订后写回 `draft.markdown`、`draft.version` 加 1、`draft.ready` true、`draft.confirmed` false |
| ④ 预审 | `{"data":{"review":{"issues":[{severity:"严重"或"建议",location,problem,basis,suggestion}]}}}` |

任务文件在 `~/.dsh/jswj-tasks/<任务号>.json`，不要手工改；只通过工具读写。

同一步优先复用任务 `sessions` 里记录的会话；修订与生成都以任务里的 `draft.markdown` 为准，不依赖聊天历史，换会话不会丢正文。

页面 D3 上传的 docx / md 会留存到知识库 `参考资料库/{层级}/{板块}/`，任务 `sources[]` 里带 `textPath`（本地纯文本）；需要读资料内容时直接读该文件，不要尝试用 `jswj_doc_read` 读 file 类型节点。

参考资料参考程度看 `sources[].mode`：

- `mirror` 统一套用模板：跳过实际起草，章节结构、正文内容、表格与图片全部按参考资料原样保留，不做内容改写，只按 GY-F003 排版。
- `template` 直接套用：沿用章节结构、行文语气、表格与内嵌图片，只按本次主题改写内容。
- `structure` 参考结构：沿用章节与写法，正文重写。
- `background` 背景资料：只取事实、数据与约束，重新起草，不照搬结构。

上传 docx 的内嵌图片已抽到 `sources[].images`（本地绝对路径）；`mirror` / `template` 模式可直接在 Markdown 中引用这些图片，`structure` / `background` 模式不要直接套用图片。

生成：逐章生成正文后，在同一回合内自动自检并修订到没有严重项，再把 `generation.status=done`、成稿正文 `draft.markdown`、`draft.ready=true`、`draft.version` 写回任务。不要让用户逐步确认自检与修订。

成稿确认：用户把意见写在 `draft.comments`。按意见逐条定向修改，只改意见指出的位置，不整体润色、不补写整节；完成后 `draft.version` 加 1、`draft.ready=true`、`draft.confirmed=false`，并写回任务。

## 知识库落位

当前知识空间根级只有三份 docx：

```
技术资料起草库（space 7698962670346636559）
├── 首页
├── 技术文件模板          ← 模板说明，不作正文落位
└── 技术资料草稿库        ← 出稿默认父节点（jswj_ping 的 draftRootToken）
```

落位规则：

- 出稿默认父节点用 `draftRootToken`；预审意见书可放在任务目录下。
- 业务目录由文档属性推导，不要让用户手工填路径：
  `{层级}/{板块}/{文件类型}/`，层级 `T0 飞机级`、`T1 系统级`、`T2 子系统级`、`T3 设备级`、`T4 软硬件级`、`T5 零件级`；
  板块如 `总体`、`电子`、`试验试飞`、`动力`；文件类型如 `需求规范`、`技术方案`。
- 写入前用 `jswj_wiki_list` 确认父节点存在且名字匹配；缺失时用 `jswj_wiki_create` 逐级创建，并复述创建结果。
- 目录不确定时先列出来问一次，不要猜一个相近的目录就写。

## 业务流 1 · 创建技术文档

| 步 | 动作 | 门禁 |
|---|---|---|
| ① 基本信息 | 收集文件名称、文件类型、密级（L1/L2/L3）、编号（可空） | 名称非空；类型与密级已选 |
| ② 文档属性 | 收集层级、板块、归档位置，推导目标目录 | 三项齐备；目录可创建 |
| ③ 参考资料 | 接收飞书云文档链接或上传件，逐份复述解析结果 | 至少一份解析成功；失败项剔除 |
| ④ 大纲与纲要 | 依据资料与模板出完整大纲（到三、四级）；只就一、二级确认要点 | 覆盖模板必备章节；要点齐备或标注「由 AI 拟稿」 |
| ⑤ 生成 | 逐章生成正文；表格结构化；图形有数据才画 | 全部章节完成 |
| ⑥ 成稿确认 | 看成稿、提意见；助手按意见定向修订 | 成稿已生成且确认 |
| ⑦ 出稿 | `jswj_render_docx` 出 Word → `jswj_publish_docx` 发布到目标目录 | 文件已落位，节点回执与链接已给出 |

补充约束：

- 编号留空时文件名只用文档名称，不生成临时编号。
- 封面签署栏与会签表留空，由标准化部门在审批环节填写。
- 修订只改意见指出的位置，不整体润色，不补写整节。

## 业务流 2 · 技术资料 AI 预审

| 步 | 动作 | 门禁 |
|---|---|---|
| ① 确认 | 说明范围与预计耗时，取得用户确认 | 已确认 |
| ② 类型与评审单 | 确认评审类型（需求规范 / 技术方案），加载评审单并复述编号与版本 | 类型与评审单适用类型一致 |
| ③ 文件与资料 | 接收受审文件（必需）与参考资料（可选） | 受审文件解析成功 |
| ④ 预审 | 按评审单审内容、按模板审格式、查术语与编号等通用项 | 三类检查均有结论 |
| ⑤ 意见与修订 | 输出意见清单并存档；询问是否协助修订 | 意见书已写入任务目录 |

补充约束：

- 意见只有两档：**严重**（不符合评审单要求或缺依据）、**建议**（可改进）。不作门禁。
- 每条意见须含位置、问题、依据、建议改法；无法定位的不写，宁可标注「缺依据」。
- 参考资料缺失时，依赖依据的检查项一律标注「缺依据」，不得默认符合。
- 协助修订限于意见指出的位置；原件保留，修订版另存，两者与意见书同目录。
- 不输出「通过」或「不通过」的结论。是否通过由人判断。

## Word 出稿规范

Markdown 结构决定 Word 结构：

- 一级标题 `#` 视为文档标题，只用于封面，不进入正文。
- `##` → 1 级标题，`###` → 2 级，`####` → 3 级；更深层级按 3 级处理。
- 表格用标准 Markdown 表格；分隔行之前都是表头，之后首列为空、其他列有短标题的续行也按多行表头处理。
- 表格前一行必须写题注：`表 {章}-{序号} 标题`；附录单号表写 `表 22 标题`。
- 图片用 `@@IMG 相对路径 宽度cm@@`，相对路径以 `baseDir` 为准；优先传绝对路径。
- 图片后一行必须写题注：`图 {章}-{序号} 标题`。
- 题注由渲染器转成 Word 的 Caption + SEQ 域，图目录、表目录据此自动生成；没有题注的图/表不会进入目录。
- 长文档先写入本地 `.md` 文件，再用 `sourcePath` 渲染，避免把整篇正文塞进工具参数。

`jswj_render_docx` 必填 `title` 与 `markdown`/`sourcePath` 之一；`docNumber` 传任务的 `basic.number`，会同时写入封面和页眉右上角。密级默认 `L2 重要/秘密`，编制默认空，校对与审核默认「待定」。生成后复述本地路径与大小。

发布：

- `jswj_publish_docx` 的 `filePath` 必须是 `jswj_render_docx` 返回的绝对路径。
- `parent` 省略时落到 `draftRootToken`；发布到任务目录时显式传该目录节点 token。
- `name` 用「{编号?}-{文件名称}-{版本}.docx」，编号为空则不带前缀。
- 发布成功后必须给出 `wikiToken` 与 `url`，并把它记为本次出稿回执。
- 发布失败时保留本地产物与返回的 `file_token`，不要重新渲染后再上传一遍。

## 排版经验（已踩过的坑，必须遵守）

### 章节编号

- 章节号以源 Markdown 标题里的编号为准，如 `## 2 引用文件和标准规范`、`### 2.1 ...`。
- 必须取消 Word 标题样式的自动多级编号，否则二级标题会跨章连续成 1.5、1.6、1.7。
- 题注的章号从当前一级标题编号读取，不要用 `STYLEREF 1 \s` 去猜，模板标题编号不一定生效。

### 列表

- 有序列表按模板编号：第一级 `a)`、`b)`，第二级 `1)`、`2)`；每个列表块重新编号，不能沿用 Markdown 里跨小节的 4、5、6、7。
- 条目之间即使有空行，只要后面仍是编号条目，就属于同一个列表块，应连续编号。
- 每个新标题下的列表重新从 1 开始。
- 无序列表左缩进约 0.35 cm，首行缩进必须显式写 `firstLineChars=0`，不能继承正文的 2 字符首行缩进，否则项目符号会显得缩进过大。

### 图目录与表目录

- 复用模板原有的「图目录」「表目录」TOC 域，不要自己再插一套目录，否则会出现两套。
- 题注用 Word 的 Caption 样式 + `SEQ 图/表` 域；图目录、表目录用模板的 `TOC \c "图"` / `TOC \c "表"` 域更新。
- 题注编号带章号时用「章-序号」；附录里的单号表（如 `表 22`）沿用源编号，不强行套章号。
- 预览稿和正式出稿走同一套渲染逻辑，目录页码都要在生成时更新好。

### 表格

- 列宽按整列内容篇幅和最长单元格共同分配；长段落多的列必须拿到更宽，不能只看表头或最长一行。
- 中文按 2 个字符宽度计算，列宽下限约 1.9 cm；表头列可适当加宽。
- 多列都很宽、总宽超版面时，按内容权重压缩，不能等比压成等宽，否则长文本列会被挤成细条。
- 分组列（序号、系统功能、研制阶段、阶段、过程、类型、类别）中，相邻相同值或空续行要纵向合并单元格，不要每行重复。
- 阶段对照表这类跨行语义列（如“高域GAC-A6飞机的研制阶段”）也要按相同值纵向合并，不能只限固定表头。
- 单元格统一单倍行距、段前段后 0，避免多行文字叠在一起。
- 表头尽量一行放得下；多行表头（如“集成与验证阶段”下再分“集成/验证/试飞测试/适航验证/总结”）要横向、纵向合并，不能当成正文行。
- 多行表头必须整块保持在同一页，所有表头段落设置 keep_with_next，避免“试飞测试/适航验证”被分页甩到下一页。
- 横向合并的表头单元格宽度必须等于所跨列宽之和，否则“验证”的右边框会和“适航验证”对不齐。
- 多行表头横向合并只能延伸到同一父表头列内，不能把“总结”并进“适航验证”；“集成/总结”要纵向跨两行。
- 表格题注放在表格前一行，图片题注放在图片后一行。

### 封面与页眉

- 封面两条横线是模板里的图形对象，清理模板时不能当批注删掉。
- 文件编号同时写入封面表格和页眉右上角，格式为 `文件编号：{编号}`。
- 编制、校对、审核、批准、版本取任务 `basic` 的对应字段；没有值时保留「待定」，不要留模板里的 `XXXX`。
- 变更记录表按 `basic.revisions` 渲染，每行一个版本；至少保留「A0 新发文件」，后续修订逐行追加版本、说明、责任人、日期。
- 首次出稿默认 `A0 新发文件`，不要自行升 A1 或加修订行；只有用户明确要求改版时才升版本。
- 会签栏和签名页是**单份文件内容**，不要写进模板；按任务 `basic.signers` 渲染，模板保持空白占位。
- 会签表增行时必须复制模板原有数据行，保留行高、字体、边框和单元格对齐，不要用默认新行重建。
- `jswj_render_docx` 的 `docNumber`、`author`、`checker`、`reviewer`、`approver`、`version` 要与任务 `basic` 一致。

### 页码

- 保留模板原有的分节：封面、修订页不显示页码；图目录/表目录用罗马数字；正文用阿拉伯数字并从 1 重新开始。
- 正文页脚保留模板的 PAGE / SECTIONPAGES 域，显示“第 X 页 共 Y 页”。
- 不能把文档收敛成单节，否则会丢失目录罗马页码和正文重新编号。

### 自动预览

- 生成完成后自动出预览稿。
- 自动预览是异步的；如果用户已经点「确认成稿」推进到下一步，旧的预览响应不得把页面状态覆盖回上一步。

### DSH 升级兼容

- DSH 升级后会校验插件的 `inject`；使用 `ctx.webServer` 必须把 `webServer` 写进 `inject`，否则页面所有 `/api/jswj` 请求都会 404，但工具本身仍然可用。
- 出现“HTTP 404 / 插件自检发现 1 项问题”时，先看插件激活诊断，再看路由是否注册，不要先怀疑飞书凭据。

### 出稿前检查清单

每次生成预览稿或正式出稿后，必须打开实际 docx 逐项核对，不能只看任务状态：

| 检查项 | 要求 |
|---|---|
| 封面信息 | 密级、名称、编制、校对、审核、批准、版本、文件编号齐全，无 `XXXX`、`A0/A1/A2` |
| 页眉 | 右上角为 `文件编号：{编号}` |
| 封面线 | 标题下、公司名上两条横线都在 |
| 图/表目录 | 只有模板原有的一套，条目和页码正确，无“未找到图形项目表” |
| 页码 | 封面/修订页无页码；目录罗马数字；正文阿拉伯数字从 1 开始，页脚“第 X 页 共 Y 页” |
| 章节编号 | 分章重新开始，如 1、1.1、2、2.1，不出现跨章连续 1.5/1.6 |
| 列表 | 第一级 `a)`、`b)`，第二级 `1)`、`2)`；每个列表块重新编号；无序列表左缩进约 0.35 cm，首行不额外缩进 |
| 表头 | 表头不被拆成“时间进度安 / 排”，多行表头层级正确 |
| 列宽 | 长文本列拿到足够宽度，不被压成细条 |
| 合并单元格 | 序号、系统功能、研制阶段、过程等分组列及阶段对照表按相同值纵向合并 |
| 多行表头 | 集成/验证/试飞测试/适航验证/总结层级正确，整块同页，验证右边框与适航验证对齐 |
| 变更记录 | 首次出稿只有 `A0 新发文件` 一行，不擅自升 A1 |
| 会签栏 | 只写本文件，不写入模板；人员和部门按任务数据 |

## 用户意见与版本规则

- 每次成稿意见记录在任务 `draft.commentHistory`，任务完成时随总结写入多维表格的「用户意见」列。
- 单条意见只作用于当前任务，不直接改全局规则。
- 版本发布时，把高频、可复用的意见归纳进本技能与页面提示，随插件一起分发给所有用户；未经归纳的意见不进入全局。

## 失败与降级

| 情况 | 处理 |
|---|---|
| 工具未注册 | 提示 `jswj-draft` 未安装或未生效，停止 |
| 凭据缺失 / 失效 | 指出缺哪项配置或错误码，请用户更新，不要反复重试 |
| `131006` 权限拒绝 | 说明应用不是知识空间成员或缺父节点容器编辑权限，不要换路径硬试 |
| `131003` 超出限制 | 说明节点数/层级/单层数量限制，改为精简目录或分批 |
| 上传 `1069909` | 文件超过 20 MB，改为压缩图片或拆分 |
| 上传 `1069913` | 文件 token 过期，重新发布 |
| Python 不可用 | 报告 `pythonPath` 与错误信息，请用户配置运行时 |
| 模板「结构不符」 | 说明 GY-F003 模板版本变化，停止出稿，不要改成无模板裸文档 |
| 多轮意见后仍有严重问题 | 列出未解决项与原因（资料不足 / 模板不适配 / 内容冲突），询问是否继续 |

## 输出要求

与用户交互使用书面语，步骤编号与本文一致。每完成一步，用一行说明当前步骤与下一步所需输入，不逐条复述本文件内容。需要用户确认时，只问当前门禁真正缺的信息，不超过 5 项。
